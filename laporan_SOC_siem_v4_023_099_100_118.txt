BAB I — PENDAHULUAN


1.1 Latar Belakang
Serangan Distributed Denial of Service (DDoS) merupakan salah satu ancaman siber paling merusak yang dihadapi organisasi modern. Serangan ini bekerja dengan cara membanjiri sistem target menggunakan volume lalu lintas jaringan yang jauh melebihi kapasitas server, sehingga layanan menjadi tidak responsif terhadap pengguna yang sah. Dampaknya mencakup kerugian finansial langsung, gangguan operasional, hingga rusaknya reputasi jangka panjang.
Dalam lingkup Security Operations Center (SOC), kemampuan mendeteksi dan merespons serangan DDoS secara cepat dan akurat adalah kompetensi fundamental. Wazuh, sebagai platform SIEM open-source yang kini banyak digunakan di industri, menyediakan mekanisme korelasi log, deteksi anomali berbasis aturan, serta integrasi dengan komponen seperti Suricata IDS yang mampu mengidentifikasi pola serangan pada lapisan jaringan.
Praktikum ini mengimplementasikan skenario nyata: dua virtual machine di-deploy sebagai endpoint Wazuh Agent di atas Microsoft Azure Student Free Tier — satu bertindak sebagai penyerang yang melancarkan HTTP Flood dan credential attack, satu lagi sebagai target (VM2MIKS) yang dipantau penuh oleh Wazuh Manager. Seluruh siklus, mulai dari provisioning VM, konfigurasi Wazuh, hingga analisis forensik pasca-serangan, didokumentasikan lengkap dalam laporan ini.


1.2 Tujuan
1. Men-deploy arsitektur Wazuh SIEM lengkap (1 Manager + 2 Agent) pada Microsoft Azure menggunakan student free tier.
2. Mendokumentasikan seluruh tahapan setup VM dan konfigurasi Wazuh secara detail.
3. Merancang dan mengeksekusi skenario HTTP Flood menggunakan ApacheBench (ab) sebagai Proof of Concept DDoS.
4. Menganalisis kemampuan Wazuh dalam mendeteksi pola anomali dan membangkitkan alert kritis (Rule ID 100210, Level 12).
5. Mendokumentasikan temuan terkait logging density, distribusi log, dan vulnerability posture sistem target.


1.3 Ruang Lingkup
Praktikum ini dilaksanakan dalam lingkungan terisolasi dan terkontrol pada Microsoft Azure. Seluruh lalu lintas serangan bersifat internal antar-VM dalam jaringan yang sama dan tidak melibatkan sistem di luar cakupan yang telah ditetapkan. Penggunaan tool ApacheBench dan Hydra dilakukan semata-mata untuk keperluan akademis dalam rangka menguji kapabilitas deteksi SIEM.

BAB III — INSTALASI DAN KONFIGURASI WAZUH


3.1 Instalasi Wazuh Manager
Wazuh Manager diinstal pada VM pertama (azurevm-manager) menggunakan Wazuh installation assistant — metode instalasi resmi yang memanfaatkan script otomatis untuk men-deploy Manager, Indexer, dan Dashboard dalam satu node. Versi yang digunakan adalah Wazuh v4.9.0.


# Download dan jalankan Wazuh installation assistant
curl -sO https://packages.wazuh.com/4.9/wazuh-install.sh
curl -sO https://packages.wazuh.com/4.9/config.yml


# Edit config.yml: isi IP Manager
nano config.yml


# Jalankan assistant untuk generate certificates
bash wazuh-install.sh --generate-config-files


# Install Wazuh Indexer
bash wazuh-install.sh --wazuh-indexer node-1


# Install Wazuh Manager + Dashboard
bash wazuh-install.sh --wazuh-server wazuh-1
bash wazuh-install.sh --wazuh-dashboard dashboard
	

3.2 Konfigurasi ossec.conf pada Wazuh Manager
File konfigurasi utama Wazuh Manager adalah ossec.conf yang berlokasi di /var/ossec/etc/ossec.conf. File ini mengontrol seluruh aspek perilaku Manager: output format, level alert yang di-log, koneksi dari agent, dan monitoring policy. Berikut adalah konfigurasi yang diterapkan dalam praktikum ini:


  

Gambar 5. Isi Konfigurasi ossec.conf pada Wazuh Manager


Poin-poin konfigurasi kritis yang perlu diperhatikan dari file ossec.conf di atas:
* jsonout_output: yes — output alert diekspor dalam format JSON, kompatibel dengan Wazuh Dashboard dan Elasticsearch.
* alerts_log: yes — seluruh alert disimpan ke file /var/ossec/logs/alerts/alerts.log untuk audit dan forensik.
* log_alert_level: 3 — hanya event dengan level 3 ke atas yang disimpan sebagai alert. Level di bawah 3 diabaikan untuk menekan volume log rutin.
* email_alert_level: 12 — email notifikasi hanya dikirim untuk alert Level 12 ke atas (critical), sehingga tim SOC tidak dibanjiri notifikasi untuk event minor.
* remote connection: secure, port 1514, protocol tcp — komunikasi antara agent dan manager menggunakan koneksi terenkripsi TCP, bukan UDP, untuk memastikan pengiriman log yang andal.
* queue_size: 131072 — buffer antrian event yang besar memastikan tidak ada log yang hilang saat terjadi spike traffic tinggi seperti saat serangan DDoS.


3.3 Instalasi Wazuh Agent pada VM Target (VM2MIKS)
Wazuh Agent diinstal pada VM2MIKS menggunakan package APT resmi dari repository Wazuh. Setelah instalasi, agent dikonfigurasi untuk menghubungi Manager melalui IP private dan diregistrasi menggunakan enrollment key.


# Import Wazuh GPG key dan tambahkan repository
curl -s https://packages.wazuh.com/key/GPG-KEY-WAZUH | gpg --no-default-keyring \
  --keyring gnupg-ring:/usr/share/keyrings/wazuh.gpg --import
echo "deb [signed-by=/usr/share/keyrings/wazuh.gpg] https://packages.wazuh.com/4.x/apt/ \
  stable main" | tee /etc/apt/sources.list.d/wazuh.list


# Install Wazuh Agent
apt-get update && apt-get install wazuh-agent


# Konfigurasi Manager IP di /var/ossec/etc/ossec.conf
WAZUH_MANAGER='10.0.0.4' WAZUH_AGENT_NAME='VM2MIKS' dpkg-reconfigure wazuh-agent


# Aktifkan dan jalankan agent
systemctl daemon-reload
systemctl enable wazuh-agent
systemctl start wazuh-agent
	

3.4 Custom Rules — Deteksi ApacheBench HTTP Flood
Untuk mendeteksi serangan ApacheBench secara spesifik, dibuat custom rule pada Wazuh Manager di file /var/ossec/etc/rules/local_rules.xml. Rule ini memanfaatkan kemampuan Suricata (yang telah diintegrasikan sebelumnya) untuk mendeteksi User-Agent ApacheBench dalam HTTP traffic, kemudian Wazuh mengkorelasikannya menjadi alert dengan level kritis.


  

Gambar 6. Isi File local_rules.xml — Custom Rule ID 100210 untuk Deteksi ApacheBench HTTP Flood


Penjelasan struktur custom rule yang dibuat:


<group name="local,suricata,ddos,">
  <!-- Rule ID 100210: Deteksi ApacheBench Tool -->
  <rule id="100210" level="12">
    <if_sid>86601</if_sid>
    <!-- Trigger jika parent rule Suricata 86601 aktif -->
    <match>ApacheBenchmark Tool User-Agent Detected</match>
    <!-- Match string dari Suricata alert -->
    <description>ApacheBench HTTP flood detected against web server target</description>
    <group>suricata,ddos,http_flood,critical_lab,</group>
  </rule>
</group>


# Keterangan parameter:
# level="12"    = Critical alert (tertinggi dalam praktikum ini)
# if_sid 86601  = Bergantung pada Suricata generic alert rule
# match         = String yang harus muncul di log untuk trigger rule ini
	

Rule ini bersifat chained — hanya aktif jika Suricata (rule 86601) terlebih dahulu mendeteksi traffic anomali, kemudian Wazuh memeriksa apakah string 'ApacheBenchmark Tool User-Agent Detected' ada dalam alert tersebut. Pendekatan two-layer ini mengurangi false positives secara signifikan karena dua kondisi harus terpenuhi secara bersamaan.

BAB IV — SKENARIO SERANGAN DDoS dan Malware


4.1 Metodologi Serangan
Skenario serangan yang diimplementasikan menggunakan dua vektor utama: HTTP Flood menggunakan ApacheBench (ab) sebagai serangan DDoS utama, dan Hydra credential attack sebagai simulasi serangan lanjutan. Karena Azure memblokir raw packet di level infrastruktur, penggunaan hping3 untuk SYN Flood tidak memungkinkan, sehingga ApacheBench dipilih sebagai alternatif yang menghasilkan beban HTTP Layer 7 yang ekuivalen.
Kami juga menggunakan konsep tools EICAR test files dimana ia akan berperan dalam pengiriman beberapa section unspicious file ke dalam lingkungan VM. Yang ini akan berbentuk sebagai identifikasi malware oleh wazuh.

Strategi Manajemen Kepadatan
* Alert Thresholding: log_alert_level: 3 memastikan hanya event level 3 ke atas yang disimpan, memotong volume log rutin secara signifikan.
* Email threshold level 12: notifikasi hanya dikirim untuk critical events sehingga mencegah alert fatigue tim SOC.
* Frequency-based correlation pada Rule 100210: rule hanya aktif ketika Suricata parent rule terpenuhi, bukan setiap HTTP request individual.
* queue_size: 131072 pada ossec.conf: buffer besar mencegah kehilangan log saat spike DDoS.
* Log rotation: mencegah disk Azure Student Tier penuh akibat akumulasi log selama serangan intens.


6.2 Logging Distribution — Distribusi Log
Wazuh menggunakan koneksi terenkripsi TCP port 1514 (dikonfigurasi dalam ossec.conf: remote/connection: secure, port: 1514) untuk mengirimkan log dari agent ke manager secara real-time.
* Real-time forwarding: event dicatat dengan akurasi milidetik (contoh: 15:39:51.729 dan 15:39:51.727 — selisih 2ms), membuktikan latensi pengiriman hampir nol.
* Resiliensi: pipeline log tetap stabil saat VM2MIKS menerima 644 request/detik dari serangan ab. Queue internal agent mencegah kehilangan event.
* Centralized correlation: semua log dari Apache, Suricata, PAM terkonsolidasi di Manager, memungkinkan korelasi cross-source yang menghasilkan Rule 100210.
* Enkripsi end-to-end: log tidak dapat disadap selama transit, konfigurasi connection: secure menggunakan TLS.


Keberhasilan pipeline ditunjukkan oleh fakta bahwa alert Level 12 (Rule 100210) terpicu secara tepat waktu pada 15:39:23 — membuktikan seluruh rantai: log Apache → Wazuh Agent VM2MIKS → Manager → Rule Engine → Alert → Dashboard bekerja end-to-end dalam hitungan detik.
BAB VII — SOAR: AUTOMATED IP BLOCKING VIA SHUFFLE
7.1 Latar Belakang SOAR
Security Orchestration, Automation and Response (SOAR) merupakan lapisan respons otomatis yang melengkapi kemampuan deteksi SIEM. Jika SIEM bertugas mendeteksi dan membangkitkan alert, SOAR mengambil alih proses respons secara otomatis tanpa intervensi manual analis SOC. Dalam konteks serangan DDoS seperti yang disimulasikan pada praktikum ini, kecepatan respons sangat kritis — setiap detik keterlambatan berarti ribuan request tambahan membebani server target.
Praktikum ini mengimplementasikan pipeline SOAR menggunakan Shuffle, platform SOAR open-source, yang menerima alert dari Wazuh dan secara otomatis memblokir IP sumber serangan menggunakan UFW (Uncomplicated Firewall) pada VM target (VM2MIKS). Pipeline ini aktif ketika Rule ID 100210 Level 12 terpicu, memastikan IP penyerang diblokir dalam hitungan detik setelah serangan terdeteksi.
7.2 Arsitektur SOAR — Wazuh + Shuffle + Flask Blocker API
Pipeline SOAR yang diimplementasikan terdiri dari tiga komponen utama yang saling terintegrasi:
•          Wazuh Manager: mendeteksi serangan dan mengirimkan alert webhook ke Shuffle ketika Rule ID 100210 (Level 12) terpicu, dengan payload berisi data alert termasuk src_ip (IP sumber serangan).
•          Shuffle (WAZUH IP BLOCKER workflow): menerima alert dari Wazuh, mengekstrak src_ip dari payload, dan meneruskan ke Flask Blocker API melalui HTTP POST request.
•          Flask Blocker API: menerima request dari Shuffle, memvalidasi API key, kemudian menjalankan skrip block_ip.sh yang menambahkan aturan DENY pada UFW untuk memblokir IP penyerang.

7.3 Konfigurasi UFW pada VM Target
Sebelum pipeline SOAR dapat berfungsi, UFW dikonfigurasi pada VM2MIKS untuk menjadi firewall yang dapat dikendalikan secara programatik oleh Flask Blocker API. Status UFW pada VM2MIKS ditunjukkan pada gambar berikut:
 
 Title: Gambar - Description: screenshot 

Gambar 17. Status UFW VM2MIKS — Rule Aktif (sudo ufw status numbered)
Dari output UFW di atas, terlihat konfigurasi firewall aktif dengan 7 aturan yang terpasang. Aturan nomor [1] menunjukkan DENY IN dari IP 85.211.194.222 (IP VM penyerang/azurevm-agent) — ini adalah hasil dari pipeline SOAR yang berhasil memblokir IP sumber serangan secara otomatis. Aturan-aturan berikutnya (nomor 2–7) adalah aturan ALLOW IN standar untuk port 22/tcp (SSH), 80/tcp (HTTP), dan 5000/tcp (Flask API) yang dibuka untuk akses dari mana saja, termasuk versi IPv6-nya.
Port 5000 khusus dibuka untuk memungkinkan Shuffle (yang berjalan secara remote) dapat mengakses Flask Blocker API. Tanpa aturan ini, request dari Shuffle tidak akan dapat mencapai API blocker yang berjalan pada VM2MIKS.

Konfigurasi node Http 1 pada Shuffle menggunakan metode POST ke URL http://20.249.5.44:5000/block yang merupakan endpoint Flask Blocker API pada VM2MIKS. Body request berisi JSON dengan field ip yang diisi secara dinamis menggunakan variabel Shuffle $exec.all_fields.data.src_ip — variabel ini secara otomatis mengambil nilai IP sumber dari payload alert Wazuh yang diterima oleh node trigger.
Header request menyertakan dua field penting: Content-Type: application/json untuk mendeklarasikan format payload, dan X-API-Key: ObiSOARBlocker2026! sebagai token autentikasi yang harus diverifikasi oleh Flask API sebelum memproses request pemblokiran. Penggunaan API key ini mencegah akses tidak sah ke endpoint blokir yang memiliki hak untuk memodifikasi aturan firewall.
7.5 Flask Blocker API
Flask Blocker API adalah komponen eksekutor dalam pipeline SOAR. API ini berjalan pada VM2MIKS di port 5000 dan bertanggung jawab menerima perintah blokir dari Shuffle, memvalidasi autentikasi, serta mengeksekusi pemblokiran IP melalui UFW.
 
 Title: Gambar - Description: screenshot 

Gambar 20. Kode Flask Blocker API (block_app.py) — Python Flask + subprocess UFW
Kode Flask Blocker API di atas mengimplementasikan logika berikut: pertama, API mendefinisikan token API_TOKEN = 'ObiSOARBlocker2026!' sebagai kunci autentikasi. Setiap request yang masuk ke endpoint /block (method POST) pertama-tama diperiksa header X-API-Key-nya — jika tidak cocok, API mengembalikan response 401 Unauthorized.
Setelah autentikasi berhasil, API mengekstrak nilai ip dari body JSON request. Jika field ip tidak ada, dikembalikan response 400 Bad Request. Jika IP valid, API menjalankan subprocess yang mengeksekusi skrip shell /usr/local/bin/block_ip.sh dengan IP sebagai argumen. Skrip ini pada dasarnya menjalankan perintah sudo ufw insert 1 deny from {ip} untuk menambahkan aturan DENY di posisi pertama UFW, memastikan aturan blokir memiliki prioritas tertinggi.
Return code dari subprocess digunakan untuk menentukan response: jika berhasil (returncode == 0), API mengembalikan 200 OK beserta detail eksekusi; jika gagal, dikembalikan 500 Internal Server Error. Mekanisme ini memastikan Shuffle dapat mengetahui apakah pemblokiran berhasil atau tidak, dan dapat mengambil tindakan lanjutan jika diperlukan.

7.7 Validasi dan Hasil
Pipeline SOAR berhasil divalidasi dengan bukti-bukti berikut: (1) IP 85.211.194.222 (azurevm-agent) tampak pada rule [1] UFW dengan status DENY IN, yang merupakan IP yang sama dengan sumber serangan ApacheBench; (2) badge counter '3' pada node Shuffle menunjukkan 3 eksekusi sukses yang berkorespondensi dengan jumlah sesi serangan selama praktikum; (3) Flask API mengembalikan returncode 0 untuk setiap eksekusi blokir, mengkonfirmasi UFW berhasil dimodifikasi.
Waktu respons keseluruhan dari deteksi hingga pemblokiran berkisar 3–5 detik, jauh lebih cepat dibandingkan respons manual analis SOC yang dapat memakan waktu beberapa menit hingga jam. Pipeline ini mendemonstrasikan nilai SOAR dalam mengurangi Mean Time to Respond (MTTR) secara drastis.




BAB VIII — KESIMPULAN


8.1 Keberhasilan Deployment dan Setup
Seluruh tahapan deployment berhasil diselesaikan: provisioning tiga VM Standard D2s v3 di Azure Malaysia West, koneksi SSH menggunakan key-based authentication, instalasi Wazuh v4.9.0 Manager dan Agent, konfigurasi ossec.conf dengan threshold optimal, serta pembuatan custom rule ID 100210 untuk deteksi ApacheBench. Kedua agen terdaftar aktif di Wazuh Dashboard dengan komunikasi terenkripsi melalui TCP port 1514.


8.2 Efektivitas Deteksi
Wazuh terbukti mampu mendeteksi serangan DDoS dengan presisi tinggi. Alert Rule ID 100210 Level 12 secara eksplisit mengidentifikasi 'ApacheBench HTTP flood' — bukan sekadar anomali generik. Integrasi MITRE ATT&CK memetakan serangan ke enam taktik secara otomatis, memberikan konteks intelijen yang kaya. Total 14.088 alert dalam 24 jam dengan 17 alert kritis membuktikan pipeline deteksi berfungsi optimal dari hulu ke hilir.


8.3 Temuan Vulnerability
Vulnerability assessment mengungkap 120 High severity vulnerabilities pada VM2MIKS, didominasi package linux-azure. Temuan Hydra menunjukkan password 'password123' berhasil dieksploitasi dalam waktu 1 detik — mengkonfirmasi perlunya kebijakan password yang lebih kuat dan implementasi MFA.


8.4 Temuan Logging Density & Distribusi
Serangan ab dengan -n 1000 -c 100 meningkatkan volume log dari baseline 0 menjadi puncak 48 event/menit. Konfigurasi ossec.conf dengan log_alert_level 3, email_alert_level 12, dan queue_size 131072 terbukti efektif dalam menjaga keseimbangan antara kelengkapan deteksi dan efisiensi sumber daya. Pipeline distribusi log Agent → Manager bekerja stabil dengan latensi milidetik bahkan di bawah beban serangan ekstrem.


8.5 Rekomendasi
* Segera patch 120 High severity vulnerabilities, terutama linux-azure package.
* Implementasi active response Wazuh untuk auto-block IP sumber ketika Rule 100210 terpicu.
* Penguatan credential policy: ganti password default dan implementasi MFA.
* Rate limiting di level web server (Apache/Nginx) sebagai lapisan pertahanan pertama.
* Enable Trusted Launch sesuai rekomendasi Azure Advisor untuk meningkatkan security posture VM.
* Tuning Suricata rules untuk mengurangi false positives dari rule ET DROP.
